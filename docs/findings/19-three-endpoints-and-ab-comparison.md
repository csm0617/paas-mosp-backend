## 二、A/B 对照（这轮最值钱的结论）

把**同一份前端产物**分别指向两个后端，用同样的 CDP 脚本打开 `/gaop/software/workloads`：

| | 对厂商后端（8098） | 对我们的后端（8099） |
| --- | --- | --- |
| URL 是否停在目标页 | ✅ | ✅（会话有效时；见下"坑"） |
| 外壳（菜单/模式/用户/授权提示） | ✅ 渲染 | ✅ 渲染 |
| `.ant-layout-content` 内容区 | **无** | **无** |
| 表格 / 数据行 | 0 / 0 | 0 / 0 |
| 快速入门弹窗 | 弹出 | 弹出 |
| STOMP | `socket 连接成功` | `socket 连接成功` |
| 页面调用的 API | 全部 200 | 全部 200（同一集合） |

**结论**：这页"内容区为空"**不是我们的实现造成的**——厂商后端在自己家里也是这个表现。
也就是说，就"厂商前端一行不改"这条门槛而言，我们与厂商**渲染等价**（并列对照，而不是自说自话）。
把内容区填起来需要的条件还没找到（未定论），见第四节。

## 三、一个工具坑（我踩了，记下来）

harness 在**启动时快照**注入的会话 token。我先后用了多个 curl 取 token，把早先的 token 留在文件里，
于是某次跑出来 `/v1/user` 401、页面被弹回登录页，看起来像"我们的会话坏了"。
重新取一次 token 并立刻验证：`/v1/user → 200`，Redis 里 `gateway-token:<token>` = `admin:admin` ✓ —— **产品没问题，是我串了 token**。

**规矩**：每次起 harness 前现取 token，并且先 `curl /v1/user` 验一次再开浏览器。
