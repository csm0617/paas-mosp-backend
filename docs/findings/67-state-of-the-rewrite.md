## 四、这套工作里已验证过的**验证方法**（可复用）

1. **A/B 逐字节对拉**：同请求打两侧；"值必然不同"的字段可忽略，但**"该字段该不该有值"不能忽略**。
2. **全分支探针**：参考值为空时先造最小数据把分支撑开（软件域那轮靠 3 行探针覆盖了 6 个分支）。
3. **集合层对拉**：顺序天然不稳定的端点（`labels`）把契约定在集合层，并**把比较方式写进文档**。
4. **独立临时 namespace 端到端**：写操作的安全姿势——建 namespace → 造最小工作负载 → 后端指过去 → 跑成功/失败 → 删 namespace。**它抓到过 mock 测不到的 bug。**
5. **离线真密码学**：拿不到对方私钥时，自造密钥对签同构 token，让真实实现去验——**不要 mock 掉验签**。
6. **可解释的 0**：两边都是 0 不算证据，**能解释"为什么是 0"才算**（`gaop`、`serviceInfoByNode` 都靠这条从"退化参考"变成"可对拉"）。

## 五、这套工作里反复出现的**失误模式**（下一轮别再犯）

| 模式 | 实例 |
| --- | --- |
| 只验形状不验值 | `/v1/licence` 的 `code` 值错了很久没发现 |
| 手抄不透明值 | 把 base64 里的 `NzQ` 抄成 `ODc`，误判"厂商机器码不稳定" |
| 读一半就下结论 | `gaop` 漏读最后一行 `isGaopApp`，连错两轮 |
| 从正确前提推错误结论 | "它在调远端 ⇒ 必为空"，被同源端点的 9 条数据否掉 |
| 两个语义接近的东西合并 | `edit()` vs `patch`、`fixedName` vs `gaop/serviceLabel`、"存在"vs"值为空" |
| 能中途失败的批处理脚本 | 补丁脚本断言失败退出，前半已落盘 ⇒ 半成品像成功 |
| 用错的量去计量 | 用例总数用 partial grep 数错（162/174 → 实际 210+） |
| 只按返回码分类 | 把 `DELETE` 端点的 400 当成"参数类" |
