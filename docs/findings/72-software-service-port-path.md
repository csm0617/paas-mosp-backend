## 2. 两处**方法层面**的教训（比端点本身重要）

**(a) 共享状态的顺序对拉会自己骗自己。**
第一版我把六种情形**依次**打厂商、再依次打我们——但第一种情形是**成功写入**，
它改了库里的路径，导致后面所有情形的前置状态都不同了（"路径已存在"那条甚至因此变成别的错）。
结果看起来"六条全不一致"，实际是**测试设计错了**。
修法：**每种情形 → 重置探针行 → 打厂商 → 重置 → 打我们 → 比对**。
（这与之前"唯一约束类用例两侧必须用不同值"是同一条纪律的另一面。）

**(b) 错误响应不能整体比对——`trace` 天然不同。**
我们的 400 信封里 `data.trace` 是 `com.csm.paas.core...`，厂商是 `com.glriverside.gaop.be...`，
**栈帧里的类名与行号永远不可能相同**。正确的比法是 `code` + `msg` + `data` 里的业务字段
（并忽略自增 `id` 这类由探针插入顺序决定的字段）。之前的轮次一直是这么比的，这一轮我一度写成整体相等，
反而制造了假差异。**把这条写进方法清单：错误路径比 `code`/`msg`/业务字段，不比 `trace`。**

## 3. 照抄点

- **四个 path 校验全在 controller 里、且在任何 DB 访问之前**（空白 → 长度 → 首字符数字 → 字符集）；
- 判重参数是 **`serviceName`**（`software.path.exist.in.service`），而端口不存在的参数是 **`port`**（`service.port.not.found`）——两个错误的参数不同，容易写反；
- `path` 先 **trim** 再校验与使用；
- 成功后**重新查一次**那一行并返回（不是拿内存里的对象）；
- 未实现：厂商随后 `notificationGateway()`（通知网关重载），与 `findings/39` 同一条待办。
