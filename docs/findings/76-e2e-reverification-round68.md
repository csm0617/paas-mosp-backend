# 端到端复验（第 68 轮）：厂商原样前端 + 我们的后端，**用户页表格内容逐字节相同**

**证据等级**：〔运行实测〕（真实前端 + 真实后端 + 真实集群，A/B 两侧）。2026-10-14。

## 1. 为什么要复验

距上一次端到端实测（`findings/26`）已经过去约 30 轮，期间改了：软件域 6 个端点、K3 授权、
服务切片 10 个端点、装配器、实体字段、错误契约……**这些改动有没有弄坏已经在用的页面，只有真跑一次才知道**。
所以这一轮不加端点，做一次**全栈复验**（这正是目标里那条硬门槛的第三项：e2e 实测）。

## 2. 方法与结果

同一份**厂商前端（一行未改）**、同一个浏览器、**同一个 token**（`max-login=1`，只能登录一次），
分别驱动我们的后端与厂商后端，抓 DOM 与截图。

**页面**：`/gaop/usermanage/account`（用户管理）

| 项 | mine | vendor |
| --- | --- | --- |
| 页面标题 | 机动平台微服务运行框架 | 同 |
| 非 2xx API | **无** | 无 |
| 表格行数 | 3（表头 / 筛选行 / 1 条数据） | 同 |
| 表头 | 序号 用户名 用户昵称 关联角色 关联席位 关联子角色 描述 更新时间 | **完全相同** |
| 数据行 | `1 / admin / 管理员 / 运维管理员门户 添加席位 / 添加子角色 / 平台管理员（集成验证初始化） / 2026-10-14 06:17:26 / 启用` | **逐字节相同**（含双重编码的中文字节） |

**我们后端在这一次会话里被前端调到的端点全部 200**：
`/v1/user`、`/v1/user/info`、`/v1/user/info`、`/v1/role/software`、`/v1/sub_role/switchRole`、
`/settings`、`/v1/mode/current`、`/v1/lang/current`、`/v1/licence/info`、`/v1/pub/quickStart`、
`/v1/image/projectList`、`/ws/info`。

## 3. 两处**已知**差异（都不是后端契约差异，如实记）

1. **WebSocket 通道**：我们的会话走了 SockJS 的 `xhr_streaming`/`xhr_send` 回退（27 个请求），
   厂商侧走原生 WS（17 个请求）。这是 **harness 的代理方式**差异（`findings/20` 已覆盖过 WS 透传），
   不是后端行为差异——页面上 `socket 连接成功` 两侧都有。
2. **HTML 长度**（55KB vs 101KB）：厂商侧页面里多了若干**导航/菜单**条目（左侧导航项）。
   页面**内容区（表格）完全相同**；差异在导航的渲染条目数上，与本次复验的页面契约无关，
   但值得记下来（可能是厂商后端多返回了某些导航相关的数据）。

## 4. 结论

- 用户管理页在**厂商原样前端**下用我们的后端渲染，**内容与厂商逐字节一致**；
- 30 轮改动**没有破坏**这条既有链路（这正是复验要证伪的东西）；
- 两处差异都已定位到 harness/导航，而不是我们实现的回归。
