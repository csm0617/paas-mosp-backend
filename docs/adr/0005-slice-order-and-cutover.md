# 切片顺序与灰度替换路径

**Status: accepted**（2026-10-14，工单 07 的落定；采纳工单内的推荐方案）

本 ADR 定死三件事：正式域的实现顺序、每个域"完成"的判定、以及新旧后端的替换与回退路径。
依据：`docs/findings/03-context-evidence.md`（12 个候选上下文的规模/耦合/不变量）与工单 06 的纵切实测。

## 1. 实现顺序（定死，顺序变更需挑战本 ADR）

| 序 | 域 | 依据 | 状态 |
| --- | --- | --- | --- |
| 1 | **软件-服务-端口**（K2 的子集） | 工单 06 已跑通，`total/count` 与厂商一致 | ✅ 已完成（门槛三条有证据） |
| 2 | **认证最小闭环**（K1 的登录/会话） | 门槛前置：厂商前端要靠它才能打我们的后端 | ✅ 已完成（工单 10；与厂商网关互通已验证） |
| 3 | **用户 / 战位**（K1 主体） | 不变量最硬；`g_role` 被 7 个 service 持有，是切分硬约束 | ← **本轮开工** |
| 4 | 授权许可（K3） | 不变量硬（JWT 验签 / 机器码交集），且与 `gaop-auth` 有边界 | |
| 5 | 国际化（K8） | 全仓唯一 DDL 唯一键（`g_sub_role.key` 之外的 DB 强制约束），体量小 | |
| 6 | 审计 / 字典 / 设置（K8 其余） | 以纯 CRUD 为主，可批量推进 | |
| 7 | 集群 / 应用视图（K10） | 105 个端点里只有 2 个触库——**它是防腐层不是领域**，直接对接 K8s，最后做 | |
| 8 | 文件与仓库（K7） | 与 `gaop-fdfs` / `gaop-image-uploader` 有边界，需连带决策 | |

**为什么把认证与用户/战位排在最前**：它们不是"业务功能"，而是**其它域的入口**。任何页面要能启动就得先过登录与 `canAdmin` 守卫（`GET /v1/user` 的 `role.key`），排在后面等于每个域都要带着一个假会话调试。K1 走完，后续 6 个域都站在一个真实的权限态上。

**为什么集群/应用视图排最后**：03 号证据把它的性质说清楚了——它是**读 K8s 的防腐层**，没有领域不变量，却有最多端点（105）与最多 K8s 语义（`TenxService` 诸转换）。先做它会用"K8s 适配"的复杂度掩盖掉真正的领域工作，也会把不清的模型固化进代码。

## 2. 每个域"完成"的判定（四条，缺一不算完成）

1. **契约**：该域端点的 L1（形状）+ L2（前端实际读取路径）全绿，新偏离必须逐条写进 `docs/findings/read-paths.json` 并给理由；
2. **e2e**：至少一条该域的真实前端用例（厂商原样前端 + 我们的后端），该用例的响应码与页面可读字段有证据；
3. **回归**：已通过的用例（具名端口、`/v1/service`、认证闭环）不退化；
4. **分层**：新代码不留 `persistent/` 之类越层包；`adapter/port` 只调 `gateway/`、`adapter/repository` 只调 `dao/`+`redis/`。

## 3. 替换与回退路径（定死）

- **并存方式**：同 namespace **双 Deployment**。重写后端另起 Deployment/Service（服务名 `paas-core`，**不占用 `gaop-be` 这个名字**），两套后端同时跑。
- **切流**：改 **Higress 路由**的上游指向（按路径前缀 `/api/gaop/**` 切，不按权重——按权重会让"一半请求走旧后端"这种状态出现在真实数据上，排障成本高于收益）。
- **回退**：把路由改回去，秒级生效。**回退不需要重新部署、不需要回滚数据库**（本阶段两套后端共用同一库与同一 Redis，见下条）。
- **数据面**：门禁阶段两套后端**共用**同一 MySQL（`gaop`）与同一 Redis。这是"兼容是门槛"的直接后果：会话要在两侧都认（已验证厂商 `gaop-be` 接受我方签发的 cookie），共库是让 A/B 对照成立的前提。
- **回退演练**：切流前必须做一次"切换→观察→切回"的完整演练并留证据，否则不算可回退。

## Considered Options

- **影子比对（mirror 流量）**：否。只读域可行，但 K1 有写路径（用户/战位增删改、级联删除事务），镜像写请求会真实改数据。
- **整体切换（停旧起新）**：否。风险最高，且节点只有 4.9 GB 内存——但这个理由本身不足以否决整体切换（内存账要单独算），真正的否决理由是**它没有回退路径**，与本 ADR 的"回退秒级"要求冲突。
- **按权重切流**：否，理由见上（真实数据上的中间态不可排障）。
- **两个后端各自独立库**：否。会让会话与 A/B 对照同时失效，等于放弃"兼容是门槛"（ADR-0001）。

## Consequences

- 内存要按"双后端并存"算账：节点单节点 4.9 GB，重写后端必须限堆（`-Xmx`），该项未定论，等切片 3 落地后实测画像再补。
- 数据库迁移从 `V0.9.0` 起编号（ADR-0004 已定），两套后端共用库意味着**厂商后端也必须能容忍我们的新迁移**——只允许加表/加列/加索引，不允许改列类型或删列。
- 每个域的 go/no-go 以第 2 节的四条判定为准，四条之外不再设"完成"标准。
