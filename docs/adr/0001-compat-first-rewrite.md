# 兼容是验收门槛，不是终态

**Status: accepted**（2026-10-14 增补：口径由"永远兼容"改为"门槛式兼容"）

厂商后端 gaop-be 有 1598 个类、约 604 个 handler；厂商前端 gaop-web（196 个 service 函数、95 条路由、三套语言包）与 87 个 Flyway 迁移（39 张表）已经把接口与数据模型固定成既成事实。我们决定：第一条纵切必须证明**厂商前端一行不改即可跑在重写后端上**，`/api/gaop/v1/*` 契约与现有 DB schema 在门槛内不可改。

门槛**之后**允许在兼容层之外做产品化演进（重命名、加字段、拆服务）——但每次演进都要先过门槛证明没打破兼容，再动手。

## Considered Options

- **门槛式兼容（选中）**：先用厂商前端与契约比对证明"重写是等效的"，再谈产品化。代价是第一阶段要背历史命名（`Tenx*`、`gaop` 包名、字段拼写错误）。
- **永远兼容**：被否——把厂商的缺陷（`${REDIS_POST:6379}`、`KAFAKA_*` 拼写、语义倒置的 `g_service.deleted`）永久固化进自有产品。
- **一开始就重定接口与表结构**：被否——会让已复刻出的前端证据与 87 个迁移全部作废，且失去"等效性"这唯一的对照物。

## Consequences

- 前端复刻产物（`/Users/csm/Desktop/Project/msop/recovered-web/`）是**验收工具**，不是待迁移资产。
- 第一阶段刻意保留 `Tenx*` 命名与 `com.glriverside.gaop` 的**对照关系**（映射写进文档），但自有代码的包名是 `com.csm.paas.core`。
- 任何意图改动响应形状或表结构的提案，必须显式挑战本 ADR 并说明它属于门槛内还是门槛后。
