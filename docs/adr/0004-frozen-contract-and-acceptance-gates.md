# 兼容硬边界与验收门槛

**Status: accepted**（2026-10-14，工单 05 的落定）

门槛内**硬不可改**（动任何一项都必须先挑战本 ADR）：

1. **端点**：厂商前端 **259** 个 service 函数命中的每一个 `/api/gaop/v1/**` 端点（`recovered-web/api-catalogue.json` 只记了其中 196 个，见 `docs/findings/02-contract-baseline.md` §1.4）——路径、方法、请求参数与响应 JSON 形状。
2. **表结构**：厂商 39 张表的 DDL（列名、类型、约束、索引语义）。
3. **K8s 代理路径**：`/api/gaop/k8s/**`——前端直接调用，属契约。
4. **迁移文件**：厂商 87 个 Flyway 迁移**冻结在 `V0.8.6`**，当成历史只读；本仓的新变更从 `V0.9.0` 起重新编号。

门槛内**可以改**：前端未使用的端点、日志与注释类字段、Java 内部结构（分层、包名、类名）、运维参数。

## 验收门槛（四条全绿才算"重写成功"）

## Considered Options

- **只锁路径与方法**：被否——响应字段一改，前端表格与表单立刻白屏；02 的契约比对正是为拦住这种破坏而存在的。
- **继续累积厂商迁移序列**：被否——厂商序列里已有两个非法命名（`V0.8.3_update_setting_table.sql`、`V0.8.4_update_audit-and-dictionary.sql`），继续搅在一起会让"哪些是厂商的、哪些是我们的"永久说不清。

## 口径更正（2026-10-14，工单 02）

前端 service 层实际有 **259** 个构造请求的函数，不是 196：`api-catalogue.json` 只收录纯字面量 URL，
漏了 49 个用 `.concat` 拼路径的与 14 个字面量（合计 63）。既有"196/196 命中 api-docs"的结论**在该受限集合内成立**，
但不代表前端只调 196 个端点；真实交集是 **255**。验收用例必须从 259 个函数反推。
（数字经工单 02 的独立复核修正过两轮：258→259；被调 283/无人调 259 → **279/263**；桶二 → **321**。）〔源：`docs/findings/02-contract-baseline.md` §1.4、§4.2〕

## Consequences

- 新字段只能以**新增键**的形式进响应 JSON，不能改名或改类型；表结构变更只能走 V0.9.0+ 的新迁移。
- 门槛过后的产品化演进（见 ADR-0001）**每次都要重跑这四条门槛**。
